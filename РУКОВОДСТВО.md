# Руководство пользователя — от А до Я

## 0. Что это за проект

**AINovelEdit** — изолированная среда для последовательной редакторской обработки машинного перевода визуальной новеллы.

Работа выполняется по главам:

```text
Японский оригинал (JA)
        ↓
Английский перевод (EN)
        ↓
Русский машинный перевод (RU)
        ↓
Проверка соответствия
        ↓
Художественная редактура
        ↓
Гуманизация русского текста
        ↓
Грамматика
        ↓
Стиль
        ↓
Финальный аудит
        ↓
output/
```

Главная задача агента — **не переводить текст заново**, а довести существующий русский перевод до естественного литературного состояния, сохраняя смысл оригинала.

При проверке соответствия:

**JA — главный источник смысла.**

**EN — вспомогательный источник**, который используется для удобного сопоставления и дополнительного контекста.

### Документация проекта

В проекте есть два разных типа документации:

- `AINovelEdit/README.md` — **техническое описание проекта**: архитектура, структура каталогов, скиллы, скрипты и принципы работы системы;
- `РУКОВОДСТВО.md` — **инструкция для человека**: подготовка данных, запуск инструментов, работа с Agent-IDE, генератором промптов, обработка глав, аудит и восстановление.

`РУКОВОДСТВО.md` находится **вне рабочей директории Agent-IDE**, потому что оно предназначено пользователю, а не агенту.

Рабочей директорией агента является:

```text
<WORKSPACE_ROOT>/AINovelEdit/
```

# 4. Нормализация исходных файлов

После добавления исходников необходимо выполнить нормализацию.

Перейдите в `<PROJECT_ROOT>` и запустите:

```bash
python tools/normalize.py --volume NN
```

Например, для тома 1:

```bash
python tools/normalize.py --volume 1
```

`NN` здесь обозначает номер нужного тома.

Скрипт подготавливает данные для работы агента.

После нормализации внутри:

```text
AINovelEdit/translates/
```

появляются:

```text
ja/
en/
ru/
```

а также отчёт сопоставления:

```text
_report/
```

### Смысловые блоки

Единица работы — **смысловой блок (микросцена)**: кластер соседних абзацев,
объединённых одним действием или говорящим (реплика + атрибуция, диалоговая
пара). В файлах `ja/`, `en/`, `ru/` блоки разделены маркером
`<!-- block: N -->`, внутри блока — естественные абзацы языка.

Блок №N — одна и та же микросцена во всех трёх языках. Число и границы
абзацев внутри блока между языками могут не совпадать — это норма, а не
ошибка: сравнение смысла идёт по блокам целиком.

Дополнительно создаётся карта блоков:

```text
_report/blocks/vNN-chYY.json
```

Она содержит для каждого блока номера абзацев каждого языка и найденные
якоря (термины словаря и числа).

### Завершённые тома

Список полностью готовых томов ведётся в:

```text
AINovelEdit/completed.md
```

Тома из этого списка **заморожены**: их текст не редактируется (скрипты
`normalize.py`, `update_merged.py`, `save_block.py`, `fix_block.py`
отказываются их обрабатывать). При расхождении терминов, имён, названий и
форм обращений истина — форма из завершённого тома; расхождение фиксируется
в отчёте аудита новой главы, но решение — в пользу уже использующейся формы.

Исключение — ручная правка пользователем: если вы решили, что термин неверен,
поправьте его в `dictionary.md` (или `addresses.md`) вручную — после этого
словарь главнее завершённого тома.

# 8. Генератор рабочих промптов

Ручная коллекция промптов в руководстве не используется. Для формирования заданий применяется генератор tools/generate_agent_prompt.py.

Для формирования задания применяется:

```text
<PROJECT_ROOT>/tools/generate_agent_prompt.py
```

Запускать его нужно из `<PROJECT_ROOT>`:

```bash
python tools/generate_agent_prompt.py
```

Генератор работает интерактивно.

---

## 8.1. Выбор тома и главы

Сначала генератор спрашивает:

- номер тома;
- название тома;
- номер главы;
- название главы.

После этого все необходимые пути формируются автоматически.

Например, пользователь выбирает:

```text
Том: 14
Глава: 2
```

Генератор сам работает с:

```text
v14-ch02.md
```

Никакие пути внутри промпта вручную менять не требуется.

---

# 9. Выбор режима работы

После выбора тома и главы генератор показывает список доступных операций.

Основные режимы:

```text
1. Начать обработку главы
2. Продолжить обработку главы
3. Полный аудит главы
4. Быстрый аудит
5. Аудит грамматики
6. Аудит стиля
7. Гуманизация / устранение машинности
8. Проверка соответствия JA/EN/RU
9. Обработка одного блока
10. Проверка кодировки
11. Разбор решений пользователя (OPEN / DEFERRED, PROVISIONAL)
```

Режим 11 применяется после того, как пользователь разобрал реестр
отложенных вопросов (`OPEN` / `DEFERRED`) и/или временные (`PROVISIONAL`)
записи словаря: агент применяет решения сразу во всех местах, где
встречается затронутое сомнение или форма, обновляет статусы и реестры,
фиксирует запись в журнале и выполняет повторный контроль.

Перед созданием промпта генератор показывает описание выбранного режима:

- что именно будет делать агент;
- какие файлы он будет затрагивать;
- какого результата следует ожидать.

Описание предназначено **только для пользователя**.

Оно не добавляется в итоговый промпт, который передаётся Agent-IDE.

После подтверждения генератор:

1. создаёт готовый рабочий промпт;
2. выводит его в консоль;
3. копирует его в буфер обмена Windows;
4. возвращается в меню.

Промпт можно сразу вставить в Agent-IDE.

---

# 10. Первый запуск главы

Для новой главы выбирается:

```text
1. Начать обработку главы
```

Агент должен определить первый необработанный блок и начать последовательную редактуру.

Работа выполняется не всей главой сразу, а блоками.

Это необходимо для:

- сохранения контекста;
- уменьшения риска потери текста;
- возможности промежуточной проверки;
- надёжного сохранения прогресса;
- восстановления после прерывания.

После обработки блока результат сохраняется в:

```text
output/vNN-chYY.md
```

Журнал работы:

```text
output/_log/vNN-log.md
```

Аудит:

```text
output/_audit/vNN-chYY.md
```

---

# 11. Продолжение обработки

Если глава уже частично обработана, не нужно запускать её заново.

Выберите:

```text
2. Продолжить обработку главы
```

Агент должен определить последнюю сохранённую позицию и продолжить с первого необработанного блока.

Повторно обработанные блоки без необходимости переписывать нельзя.

Это особенно важно для длинных глав.

---

# 12. Работа с отдельным блоком

Если требуется обработать только один конкретный блок, используется:

```text
9. Обработка одного блока
```

Генератор дополнительно спрашивает номер блока.

Например:

```text
Номер блока: 17
```

Агент работает только с указанным блоком.

Этот режим используется для:

- точечного исправления;
- повторной проверки;
- исправления найденной ошибки;
- проверки спорного места;
- восстановления после неудачной обработки.

# 13. Основной порядок редакторской обработки

Редакторская обработка должна сохранять следующий принцип:

```text
JA / EN
↓
Проверка смысла
↓
Редактура
↓
Гуманизация
↓
Русская проза
↓
Грамматика
↓
Механические проверки
↓
Стиль
↓
Финальный аудит
```

---

## 13.1. Проверка соответствия

Проверяется:

- не потерян ли смысл;
- не добавлено ли то, чего нет в оригинале;
- не изменены ли субъект и объект действия;
- не изменена ли модальность;
- не потеряно ли отрицание;
- не изменены ли условия;
- не изменены ли причинно-следственные связи;
- не искажены ли действия персонажей;
- не изменены ли отношения между персонажами.

При конфликте:

```text
JA > EN > RU
```

EN используется как вспомогательный перевод.

---

# 14. Художественная редактура

После проверки смысла русский текст приводится к нормальному литературному виду.

Цель:

- убрать неестественные конструкции;
- сделать фразы читаемыми;
- сохранить голос персонажей;
- сохранить авторский смысл;
- не превращать текст в чрезмерно литературную адаптацию;
- не добавлять информацию от себя.

Редактура не должна менять содержание сцены.

---

# 15. Гуманизация

Отдельно проверяется машинность текста.

Особое внимание:

- калькам;
- буквальному копированию структуры английского;
- неестественному порядку слов;
- шаблонным оборотам;
- машинным связкам;
- чрезмерной номинализации;
- неестественным усилителям;
- одинаковому синтаксису соседних предложений.

Цель — получить естественный русский текст, а не просто заменить отдельные слова.

---

# 16. Русская проза

Текст должен соответствовать нормальной русской художественной прозе.

Проверяются:

- оформление диалогов;
- авторские ремарки;
- абзацы;
- тире;
- кавычки;
- многоточия;
- оформление мыслей;
- порядок слов;
- естественность повествования.

При этом не следует автоматически исправлять каждую необычную конструкцию.

Если конструкция соответствует голосу персонажа или авторскому стилю, её необходимо сохранить.

---

# 17. Контроль грамматики

Грамматическая проверка выполняется отдельно от стилевой.

Проверяются:

- падежи;
- согласование;
- управление;
- число;
- род;
- время;
- вид;
- залог;
- возвратность;
- субъект и объект действия;
- правильность использования `-ся`;
- деепричастные и причастные конструкции.

Особое внимание следует уделять конструкциям, где русский перевод меняет распределение ролей.

Например:

```text
Маликорна и вовсе лишились жезла
```

может быть грамматически неверным, если Маликорна является объектом действия.

В таком случае:

```text
Маликорна и вовсе лишили жезла.
```

Это не просто стилистическая правка.

Это ошибка управления, залога и актантной структуры.

---

# 18. Механическая проверка грамматики

Перед полноценным грамматическим аудитом может использоваться:

```bash
python scripts/grammar_scan.py
```

Скрипт является **предварительным фильтром**.

Он может находить подозрительные конструкции, например:

- английский passive → русское `-ся`;
- `был + причастие`;
- потенциально неправильное распределение субъекта и объекта;
- конструкции вида `X's Y was ...`.

Результаты механического сканирования не являются окончательным решением.

Каждое срабатывание проверяется человеком/агентом по контексту.

---

# 19. Проверка стиля

После грамматики выполняется независимый стилевой аудит.

Проверяются:

- тавтология;
- повторы;
- повтор однокоренных слов;
- неудачные коллокации;
- смысловая избыточность;
- кальки;
- номинализации;
- машинные усилители;
- неестественный порядок слов;
- шаблонные конструкции;
- тяжёлые или неестественные фразы.

Стилевой аудит не должен превращаться в автоматическое переписывание всего текста.

Исправляются только реальные проблемы.

---

# 20. Механический стилевой скан

Для предварительного поиска кандидатов используется:

```bash
python scripts/style_scan.py
```

Это также **не финальный арбитр**.

Скрипт только показывает потенциально подозрительные места.

После этого агент проверяет их в контексте.

---

# 21. Важное правило для детекторов

Новые правила механических сканеров нельзя добавлять только потому, что конструкция кажется подозрительной.

Новое правило добавляется только если:

1. в реальной главе обнаружена подтверждённая проблема;
2. подтверждено, что конструкция действительно нежелательна;
3. правило достаточно узкое;
4. добавлен положительный пример проблемной конструкции;
5. добавлены отрицательные примеры нормальных конструкций;
6. тесты проходят без новых ложных срабатываний.

Главный принцип:

> Ложное срабатывание опаснее пропущенного сомнительного кандидата.

Особенно это важно для художественного текста.

# 22. Финальный аудит

Для полной проверки главы используется:

```text
3. Полный аудит главы
```

Финальный аудит должен независимо проверить:

### GRAMMAR AUDIT

- грамматику;
- управление;
- падежи;
- согласование;
- залог;
- актанты;
- `-ся`;
- другие подтверждённые грамматические проблемы.

### STYLE AUDIT

- тавтологию;
- повторы;
- однокоренные повторы;
- коллокации;
- избыточность;
- кальки;
- машинность;
- неестественные конструкции.

### TRANSLATION AUDIT

- соответствие JA;
- соответствие EN;
- отсутствие смысловых потерь;
- отсутствие добавлений;
- сохранение отрицаний;
- модальность;
- условия;
- субъектов и объектов;
- причинно-следственных связей.

Если STYLE AUDIT не выполнялся, нельзя утверждать, что глава полностью проверена.

---

# 23. Аудит не должен автоматически переписывать всё

Аудит предназначен прежде всего для обнаружения и подтверждения проблем.

Необходимо различать:

```text
ERROR
WARNING
CANDIDATE
PASS
```

`ERROR` — подтверждённая проблема.

`WARNING` — подозрительное место, требующее внимания.

`CANDIDATE` — возможная проблема, но недостаточно оснований для обязательного исправления.

`PASS` — результат проверки участка/абзаца/главы, а не тип ошибки.

# 38. Предисловие переводчика и склейка тома

## Файл предисловия

Предисловие переводчика хранится отдельным файлом и заполняется **вручную**:

```text
prefaces/v<NN>.md
```

Например: `prefaces/v14.md`.

В нём указываются:

```markdown
# Предисловие переводчика

**Том:** 14

**Версия перевода:** 1.0

**Репозиторий:** <https://github.com/...>

**Переводчик:** <ссылка на переводчика>

**Дата последнего редакта:** 2026-09-20
```

Файл можно свободно править в любой момент. Скрипты его **никогда не
изменяют** и не создают.

## Вставка в том

При склейке тома предисловие добавляется **первым блоком**, отделяется
горизонтальной чертой, после него идут главы и эпилог:

```bash
python tools/merge_volume.py --volume 14
```

Результат:

```text
AINovelEdit/output/14-merged.md
AINovelEdit/output/14-merged.pdf
```

PDF собирается автоматически. Движок выбирается так:

1. если установлен `typst` / `xelatex` / `lualatex` / `pdflatex` — PDF
   собирает `pandoc` с этим движком;
2. иначе (**без LaTeX**) — pandoc собирает HTML, а headless **Chrome/Edge**
   печатает из него PDF (кириллица и изображения обрабатываются браузером);
3. если нет ни движка, ни браузера — печатается понятная ошибка, а `.md`
   всё равно создаётся.

Движок можно задать явно:

```bash
python tools/merge_volume.py --volume 14 --pdf-engine browser
python tools/merge_volume.py --volume 14 --pdf-engine none   # без PDF
```

Оформление PDF:

- **цвет ссылок** — `--pdf-link-color "#1f4e79"` (по умолчанию тёмно-синий;
  применяется и в Typst, и в браузерной печати);
- **рамка и прочие Typst-стили** — файл `prefaces/pdf-header.typ`
  (заполняется вручную, подключается автоматически для движка typst;
  можно указать другой файл: `--pdf-header <файл>`).

  Пример рамки — уголки `border.webp` на четырёх углах каждой страницы
  (файл уже содержит рабочий рецепт):

  ```typst
  #let corner = image("border.webp", width: 5cm)
  #set page(background: {
    place(top + left, corner)
    place(top + right, rotate(90deg, corner))
    place(bottom + right, rotate(180deg, corner))
    place(bottom + left, rotate(270deg, corner))
  })
  ```

  ⚠️ Пути в Typst — **от корня проекта** (папка, из которой запускается
  `merge_volume.py`): `image("border.webp")` — верно;
  `image("D:/.../border.webp")` и `image("../../images/…")` — Typst их
  отвергает (абсолютные пути и выход за пределы корня запрещены).

Правила:

- если `prefaces/v<NN>.md` отсутствует — том собирается без предисловия
  (это не ошибка, в консоли печатается уведомление);
- предисловие обрабатывается как обычный Markdown: маркеры блоков
  удаляются, маркеры изображений `<!-- img_NN-K -->` заменяются картинками;
- внутри предисловия можно использовать обычную Markdown-разметку
  (списки, ссылки, курсив);
- **разрывы страниц**: предисловие занимает отдельную страницу (после
  разделителя `***` идёт разрыв), и **каждая глава начинается с новой
  страницы**. Для движка typst это делается автоматически; в браузерном
  режиме — теми же правилами CSS (`h1 { page-break-before: always }`);
- если PDF через браузер не удался, рядом остаются промежуточные
  `14-merged.html` и `14-merged.css` — по ним видно причину; при успешной
  сборке они удаляются.

## Смена версии

Чтобы обновить версию или дату — отредактируйте `prefaces/v<NN>.md`
вручную и снова запустите склейку тома: предисловие будет взято из файла
в актуальном виде.
