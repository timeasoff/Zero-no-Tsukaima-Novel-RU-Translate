# AGENTS.md — общие указания для агента (AINovelEdit)

## Назначение

Проект доводит машинный русский перевод японской новеллы до художественного
состояния, сверяясь с японским оригиналом (JA) и английским переводом (EN).

**Главная задача — не переводить текст заново**, а редактировать существующий
русский перевод, сохраняя смысл оригинала.

## Приоритет источников (областная модель)

Единой лестницы «кто всегда прав» нет: у каждого источника своя область
авторитета. Исключение — область смысла: там иерархия жёсткая
(**JA > EN**, см. следующий подраздел); областная модель ниже относится к
словарю, завершённым томам и обращениям.

### Смысл японского оригинала: JA → RU (EN — только справочный)

```text
JA = authoritative source of truth (авторитетный источник истины)
RU = translation under review (проверяемый перевод, предмет проверки)
EN = reference only (только справочный материал)
JA > EN при конфликте
```

- **JA — авторитетный источник истины**: смысл проверяется по паре
  **JA → RU** (не EN → RU и не JA → EN → RU: EN не является
  промежуточным эталоном перевода).
- **EN — только справочный материал**: полезен для выявления пропусков,
  проверки интерпретации, разрешения неясностей, обнаружения возможных
  расхождений.
- Сырой RU (`translates/ru`) никогда не является доказательством исходного
  смысла — это вспомогательное сырьё.
- Не считать английскую формулировку более правильной, если она расходится
  с японским оригиналом; расхождения JA ↔ EN не решаются молча —
  фиксируются в логе (см. «Расхождения JA ↔ EN» ниже).
- EN — **reference only**: при конфликте EN и JA приоритет всегда у JA
  (JA > EN), а совпадение RU с EN само по себе не является доказательством
  корректности перевода (канонический текст правила — в скилле
  `semantic-analyzer`, раздел «Иерархия источников»).

### Структура выходного текста: смысловые блоки

Единица обработки — **смысловой блок (микросцена)**: кластер соседних
абзацев, объединённых одним действием/говорящим (реплика + атрибуция,
диалоговая пара). Блоки размечены маркером `<!-- block: N -->` во всех
трёх файлах (`translates/{ja,en,ru}`); блок N — микро-сцена JA. EN/RU
выровнены по якорям приблизительно — их границы сдвигаются на соседние сцены (см. «Известные ограничения»), содержание ED_RU бери по JA.

- Внутри блока число и границы абзацев **могут не совпадать** между языками —
  это норма, а не рассинхрон. Сравнение смысла ведётся по блокам целиком.
- Перевод и редактура идут поблочно: блок = одна итерация агента
  (сохранение — `save_block.py --block N`, где N — номер смыслового блока).
- Абзацную структуру русского текста внутри блока агент выбирает сам
  (по правилам `russian-prose-rules`), не подгоняя её под EN и не подгоняя
  под JA: смысл сверяется по блоку, структура — по законам русской прозы.
- Мерж и проверки (`update_merged.py`, `check_alignment.py`,
  `grammar_scan.py`) работают по блокам; `format_scan.py` — построчно
  по output-файлу (оформление не требует merged).

### Завершённые тома — источник истины (заморожены)

Список завершённых томов ведётся в [completed.md](completed.md). Правила:

- **Завершённые тома не редактируются**: `tools/normalize.py`,
  `update_merged.py`, `save_block.py`, `fix_block.py` отказываются их
  обрабатывать. Текст `output/vNN-*.md` завершённых томов — read-only.
  (`tools/` — каталог в корне РЕПОЗИТОРИЯ, рядом с `AINovelEdit/`; внутри
  `AINovelEdit/` лежит только `scripts/`.)
- **При расхождении терминов, имён, названий, заклинаний, титулов и форм
  обращений истина — форма из завершённого тома.** Словарь `dictionary.md`
  при этом остаётся каноном лексической идентичности; если словарь и
  завершённый том расходятся — побеждает завершённый том, если пользователь
  вручную не поправил словарь (тогда главнее словарь).
- Расхождение фиксируется в отчёте аудита главы
  (`output/_audit/vXX-chYY.md`, раздел «Расхождения с завершёнными томами»),
  решение — в пользу уже использующейся формы.
- Завершённый том можно читать как референс (терминология, стиль персонажей,
  оформление речи, обращения).

### dictionary.md — каноническая лексическая идентичность

Словарь авторитетен в своей области (имена, названия, установленные
термины, заклинания, титулы, канонические соответствия), но
**канонический термин ≠ механическая строковая замена**: словарь
определяет каноническое значение и лексическую идентичность, а не
единственную поверхностную форму в каждом русском предложении
(скилл `terminology-dictionary`).

### addresses.md — каноническая форма существующего обращения

Справочник определяет форму **уже установленного** обращения; он не даёт
права создавать новое обращение «из воздуха» (скилл `forms-of-address`).

## Структура каталогов

Корень рабочей директории агента — `AINovelEdit/`. Конкретные абсолютные пути
для текущего тома/главы указываются в промпте, который генерируется
инструментом `tools/agent_workflow.py` (не меняй пути вручную).
Имена файлов тома — без ведущего нуля: `v2-ch06.md`, `v2-log.md`
(translates/, output/, merged/, \_prefilter/). В `output/_audit/` том 2

## Правила работы

- Работай по главам, единица итерации — смысловой блок (`<!-- block: N -->`);
  результат сохраняй через `scripts/save_block.py`, точечные исправления —
  через `scripts/fix_block.py`.
- **Канал передачи текста правок.** Не передавай кириллицу и вообще не-ASCII
  текст в аргументах командной строки и в конвейерах через shell
  (`--text "…"`, переменные PowerShell, `|`): такой канал искажает символы —
  в файл попадают подмены букв («чтобы» → «ттобы»), порча кодировки и дубли
  маркеров (инцидент при аудите v04-ch01). Порядок:
  - **Точечные исправления в блоке (основной способ):** создай UTF-8 JSON
    со списком замен `[["старое", "новое"], …]` и передай скрипту через
    `--replace-file <путь>`:
    `python scripts/fix_block.py --file vXX-chYY.md --block N --replace-file fixes.json`
    (доступен `--dry-run` для предпросмотра). Никаких одноразовых Python-драйверов
    писать не нужно — скрипт сам находит подстроку в блоке, заменяет её,
    нормализует блок и проверяет целостность файла.
  - **Полная замена блока:** пиши текст в UTF-8 файл инструментом редактирования,
    а скрипту передавай только ПУТЬ —
    `save_block.py --text-file <файл>` / `fix_block.py --text-file <файл>`.
  - После правки сверяй результат (`git diff` — только ожидаемые строки):
    оба скрипта после записи проверяют UTF-8, уникальность/порядок маркеров
    и совпадение записанного с заданным текстом и откатывают файл при расхождении.
- Незавершённые главы находятся по маркерам `<!-- block: N -->` в `output/`.
- Все отклонения от источников (удаления, расхождения JA ↔ EN, сомнения)
  фиксируются в `output/_log/vNN-log.md`. **Молча ничего не удаляется.**
- Предисловие переводчика (`prefaces/vNN.md` в корне репозитория) — ручной
  файл: агент его **не создаёт, не редактирует и не удаляет**. Он вставляется
  в начало смерженного тома при склейке (`tools/merge_volume.py`).
- При склейке тома (`tools/merge_volume.py --volume NN`) в него попадают все
  файлы `output/vNN-*.md`: главы по номеру, затем эпилог (`vNN-epilogue.md`),
  послесловие (`vNN-afterword.md`) и прочие служебные секции — если они есть.
- Места, требующие решения человека, помечаются `<!-- ??? -->`.
- **Сноски переводчика `^[Пр. пер: …]` в output при аудировании не удаляются и не переписываются** —
  это намеренные ручные вставки человека, сделанные осознанно (см. «Зона
  человека и зона агента в маркерах»): сигнал «сноски нет в JA → ADDITION»
  на такие сноски — ложный, решение по нему `FALSE_POSITIVE` / `PRESERVED`.
- Термины — только по `dictionary.md`; обращения к персонажам — по
  `addresses.md`. Словарная запись — каноническое **лексическое соответствие**,
  а не механическая замена: контекстные формы (например, «знать» вместо
  «аристократы» там, где речь о сословии как слое) допустимы, если точнее
  передают смысл и синтаксис русского предложения (скилл
  `terminology-dictionary`, раздел «Словарный термин ≠ механическая замена»).
- Авторские слова отдельным абзацем после реплики оформляются **без тире**
  (самостоятельное предложение); тире добавляется только если JA/EN показывают
  продолжение конструкции прямой речи. Знак препинания, которого нет в
  исходной конструкции, не добавляется ради интонационной связи абзацев.
  Границы абзацев в прямой речи определяются синтаксисом и композицией
  авторского текста, а не механически; типографический перенос внутри одной
  записи `ED_RU` нового alignment-абзаца не создаёт (скилл
  `russian-prose-rules`, разделы «Абзацное оформление прямой речи» и
  «Авторские слова отдельным абзацем после реплики»).
- Перед изменением текста учитывай этот файл, словарь и правила скиллов.
- **Первичная проверка — подготовительный этап, а не отдельная фаза.**
  Если пользователь поручил обработать/перевести главу — это уже
  разрешение на выполнение. После проверки среды (инструкции, структура,
  скиллы, словарь, источники JA/EN/RU, текущее состояние) агент обязан
  в ТОМ ЖЕ запуске перейти `ANALYSIS → CLASSIFICATION →
PROVISIONAL RESOLUTION → EXECUTION` и начать первый блок главы.
  В этом режиме запрещено: спрашивать «начинать ли / продолжать ли»,
  возвращать только план, завершать ответ после подготовки, ждать
  следующего сообщения пользователя. Исключение — только действительно
  блокирующая неопределённость (см. «Неопределённость: non-blocking
  and blocking»). Локальные и средние неопределённости решаются как
  `PROVISIONAL` и работу не останавливают.
- Любой сигнал (сканер, паттерн, предфильтр, подозрение) проходит полный
  жизненный цикл DETECT → INVESTIGATE → COMPARE → CLASSIFY → DECIDE →
  EDIT → RECHECK → RECORD; обнаружение — только повод для проверки,
  а не разрешение на правку (см. «Жизненный цикл любого сигнала» ниже).
- **Предпочтение редактора не является доказательством ошибки.** Если
  формулировка грамматически корректна, сохраняет смысл, соответствует
  JA/EN, канону терминологии и обязательным правилам оформления — она
  остаётся, даже если существует субъективно более привлекательный вариант
  («красивее», «литературнее», «естественнее», «ближе к EN», «ближе к
  словарной форме», «без повтора», «привычнее», «более профессионально»).
  Leave-Unchanged Accuracy важнее количества правок; **ноль правок —
  допустимый итог аудита, но не критерий его качества**: критерий
  качества — полнота (recall) на размеченном корпусе ручных правок
  (`_work/qa_corpus`), а не отсутствие жалоб на текст.
- **Не выдумывай JA-доказательство.** Утверждение «в JA сказано X» требует
  реального X в доступном JA-контексте. Реконструировать отсутствующую
  японскую фразу, ссылаться на похожее место как на доказательство,
  приписывать JA значение — запрещено. Нет точной опоры → «JA прямо этого
  не подтверждает», пометка `???`, запись в журнал.
- Обратный перевод (back-translation) — **диагностический инструмент**,
  а не арбитр над JA: он ловит смену субъекта, числа, роли, потерю
  модальности, направления действия и смысловой сдвиг, но нельзя
  исправлять корректный русский только потому, что его обратный перевод
  не совпал с EN. JA остаётся смысловым источником.
- **Модальность неприкосновенна.** Редактор не усиливает и не ослабляет:
  вопрос, сомнение, предположение, возможность, необходимость,
  категоричность, приблизительность, эмоциональную степень. JA-размышление
  или вопрос (например, もう少し時間が必要なんだろうか) не превращается в
  уверенное утверждение ради «естественности русского».
- **UNCERTAINTY ≠ STOP.** Неопределённость не является автоматически
  блокирующим условием. Встретив неоднозначный термин, фразу или спорное
  место, агент сначала определяет масштаб неопределённости и её влияние
  на дальнейшую работу и по возможности продолжает обработку с
  provisional-решением, а не останавливает главу вопросом пользователю
  (см. «Неопределённость: non-blocking и blocking» ниже).
  **PROVISIONAL ≠ CANONICAL**: временное решение не превращается в канон
  словаря без подтверждения пользователя.

## Git: коммит только с явного подтверждения пользователя

**Единое правило с приоритетом над всеми локальными инструкциями.**
Ни один скилл, скрипт, подагент, автоматизированный процесс или иной
механизм не может отменить этот запрет.

- Агент не имеет права выполнять `git commit` без явного предварительного
  подтверждения пользователя.
- Завершение задачи, успешные проверки, просьба сохранить прогресс или
  общее разрешение редактировать файлы **не означают разрешения на
  коммит**.
- Агент может предложить коммит: назвать предполагаемое сообщение коммита
  и перечень изменений, которые в него войдут.
- Коммит разрешается только после однозначного подтверждения пользователя,
  относящегося к конкретному набору изменений.
- Без подтверждения изменения остаются незакоммиченными.
- Запрет распространяется на все skills, скрипты, подагентов,
  автоматизированные процессы и любые другие механизмы, способные вызвать
  коммит (включая «обязательный коммит после сохранения» и «коммит при
  завершении задачи» — такие формулировки запрещены).
- Обычные Git-операции, не создающие коммит и не изменяющие состояние
  проекта (`git status`, `git diff`, `git log`, `git show`, сравнение
  ревизий для анализа), разрешены.

## Жизненный цикл любого сигнала (обязателен для всех слоёв)

Главное системное правило проекта. Любой автоматический или ручной сигнал
проходит один и тот же цикл:

```text
DETECT → INVESTIGATE → COMPARE → CLASSIFY → DECIDE → EDIT → RECHECK → RECORD
```

1. **DETECT** — сигнал обнаружен (сканером, скиллом или человеком).
2. **INVESTIGATE** — изучен контекст: предложение, абзац, соседние реплики,
   функция места в тексте.
3. **COMPARE** — проверены JA / EN и соответствующие проектные правила
   (словарь, обращения, грамматика, оформление).
4. **CLASSIFY** — определена природа места (см. «Classification и
   disposition» ниже).
5. **DECIDE** — принято решение, нужна ли правка.
6. **EDIT** — правка выполняется только при наличии основания.
7. **RECHECK** — результат повторно проверен (правка = новый непроверенный
   текст).
8. **RECORD** — решение зафиксировано в отчёте/журнале.

### Критически важно

**Ни один scanner, pattern, regex, prefilter или heuristic не имеет права
сам по себе разрешать редактуру.** Обнаружение паттерна означает только:

> «здесь требуется проверка».

Оно не означает:

> «это ошибка».

## Classification и disposition (разные вещи)

**Два этапа: обнаружение (evidence) и решение (decision).**

### Evidence stage — обнаружение

Предфильтры, независимые аудиторы A/B/C и детерминированный
`omission_precheck` только находят и описывают кандидата: `severity`
(ERROR / WARNING / CANDIDATE), при необходимости `confidence`,
`issue_type`, `evidence` / `reason`. Финальные classification и disposition
здесь **не обязательны** — решение ещё не принято (`detection/evidence ≠
final decision`). Это нормально: `omission_precheck` законно выдаёт только
`severity=CANDIDATE` с `confidence` и никакого disposition не имеет.

### Decision stage — решение

**Classification** — характеристика обнаруженного места:

- `ERROR` — однозначная ошибка;
- `WARNING` — очень вероятная проблема, но возможна допустимая
  интерпретация;
- `CANDIDATE` — место требует проверки, уверенно ошибкой не названо;
- `PASS` — проблем не обнаружено.

Конкретный аудит может иметь дополнительные внутренние статусы, если они
уже закреплены в его скилле.

**Disposition** — итоговая судьба проверенного кандидата:

- `FIXED` — исправлено;
- `FALSE POSITIVE` — ложное срабатывание;
- `PRESERVED — FUNCTIONAL` — сохранено как функциональный приём;
- `PRESERVED — JA/EN` — сохранено после проверки источников;
- `PRESERVED — CHARACTER VOICE` — сохранено из-за голоса персонажа;
- `ACCEPTABLE ADAPTATION` — допустимая художественная адаптация;
- `USER DECISION` — решение пользователя;
- `???` — недостаточно данных, требуется решение человека.

Кандидат, дошедший до Decision stage, обязан получить и classification, и
disposition; кандидат, живущий только в evidence stage (находка A/B/C,
candidate pre-check), classification/disposition ещё не имеет — это не
нарушение, а отложенный до Analyzer (для SMA) решение. Не каждый
обнаруженный сигнал превращается в исправление. Слияние
нескольких кандидатов в одно решение разрешено только с явным
перечислением всех объединённых кандидатов.

Для смыслового аудита (SMA) Decision stage выполняет Analyzer по ДВУМ
независимым осям (скилл `semantic-analyzer`, раздел «Две оси решения»):
ось достоверности `fidelity` — `MEANING_SHIFT` / `COMPONENT_LOSS` /
`ADDITION` / `MISSING` / `RUSSIAN_ERROR` / `FORMAT`; ось действия `action`
— `FIXED` / `REPORT_ONLY` / `PRESERVED` при исходе `status`
`CONFIRMED_ERROR` / `DISPUTED` / `FALSE_POSITIVE` (`OPTIONAL` упразднён:
«допустимое улучшение» не является классом потери)
(см. «Legacy: автоматический semantic audit», рабочая архитектура SMA).

## Неопределённость: non-blocking и blocking

**UNCERTAINTY ≠ STOP.** Обнаруженная неоднозначность (новый термин,
спорная форма, сомнительное место) сначала классифицируется по масштабу
влияния, а не автоматически останавливает работу.

### 🟢 Локальная — не блокирует

Вопрос относится к одному термину, одной фразе, одному названию,
локальному стилистическому решению или единичному спорному месту — и не
препятствует безопасному продолжению перевода. Агент НЕ останавливает
обработку. Он обязан:

1. исследовать JA → EN → `dictionary.md` / `addresses.md` → контекст →
   этимологию (это **порядок исследования, а не иерархия авторитета**:
   при конфликте EN и JA действует JA > EN — см. «Приоритет источников»);
2. выбрать наиболее обоснованную рабочую форму;
3. использовать её временно, пометив как `PROVISIONAL` (если
   подтверждение действительно необходимо);
4. записать решение в журнал (с перечнем мест использования);
5. продолжить обработку;
6. вернуться к вопросу на финальном аудите или при решении пользователя.

### 🟡 Средняя — не блокирует при traceability

Решение может повлиять на несколько последующих мест, но перевод можно
безопасно продолжить: выбрать временное решение, зафиксировать его как
`PROVISIONAL`, обеспечить прослеживаемость всех мест, где оно
использовано, и продолжить. Временное решение не считается окончательным
каноном.

### 🔴 Блокирующая — редкий случай

Останавливать работу можно только если без решения:

- невозможно корректно продолжить сам перевод;
- существует высокий риск массового распространения неверного решения;
- дальнейший текст зависит от одного из взаимоисключающих вариантов;
- невозможно безопасно использовать provisional-решение;
- вопрос требует изменения уже утверждённого канона;
- дальнейшая работа сделает последующую корректировку практически
  неконтролируемой.

Даже в этом случае блокировать по возможности **только зависимый
участок**, а не всю главу.

### PROVISIONAL ≠ CANONICAL

**PROVISIONAL не означает WAIT**: обнаружение нового provisional-термина
само по себе не является блокирующей неопределённостью — подтверждение
пользователя не ожидается.

Запрещено записывать неподтверждённую форму как окончательный канон
словаря. Запись provisional-формы в `dictionary.md` допустима **только
с явным статусом `PROVISIONAL`**; такая запись автоматически каноном
не считается. Путь решения:

```text
PROVISIONAL → USER CONFIRMED → CANONICAL
PROVISIONAL → REJECTED → REPLACE ALL AFFECTED OCCURRENCES
```

Обязательная цепочка:

```text
PROVISIONAL → LOG → USE → CONTINUE → REPORT → CONFIRM → CANONICAL
```

в том числе: **сообщить о каждом новом PROVISIONAL-термине в итоговом
отчёте блока/главы**. Все места использования provisional-формы должны
быть прослеживаемы: запись в журнале + явная пометка `PROVISIONAL`
в `dictionary.md` (вместо канонической).

### Ключевое правило автоматизации

Агент сначала пытается продолжить работу безопасным временным решением
и только потом рассматривает запрос пользователя как блокирующее
действие:

```text
новый термин
→ исследовать JA / EN / dictionary / контекст / этимологию
→ оценить масштаб неопределённости
→ локальная или средняя?
   ├─ да → provisional → log → продолжить
   └─ нет → возможно ли безопасное продолжение?
      ├─ да → provisional → log → продолжить
      └─ нет → запросить решение (минимально достаточный участок)
```

### OPEN / DEFERRED — отложенные пользователем вопросы

Открытые вопросы не блокируют прохождение главы. Если пользователь явно
отложил спорный пункт, агент сохраняет его в audit/log со статусом
`OPEN` / `DEFERRED`, **не считает его решённым** и продолжает обработку
остальных блоков. Отложенные вопросы разбираются отдельным финальным
проходом после завершения всей главы. Последующие эвристики и проверки
не имеют права закрывать DEFERRED-вопрос автоматически.

## Порядок обработки (pipeline)

Слои аудита независимы: каждый ищет свой класс ошибок и не подменяет соседний.

```text
translation-audit       → смысл / соответствие JA и EN (EN — опора проверки
                          структуры/знаков, JA — арбитр смысла)
novel-editor            → художественная редактура
self-review             → самопроверка на галлюцинации (перед сохранением)
save-progress           → сохранение через save_block.py
                          + update_merged.py + check_alignment.py
russian-humanizer       → машинность / translationese / AI-штампы
russian-prose-rules     → оформление русской прозы (речь, мысли, курсив)
check_records.py        → шаг 0: слитные записи «наррация. — Реплика»
                          (реплика обязана начинаться с новой строки)
address_scan.py         → шаг 0: обращения (кандидаты forms-of-address)
grammar_scan.py         → шаг 0: механический предфильтр грамматических кандидатов
russian-grammar-control → грамматика / падежи / актанты / залог (разбор кандидатов)
style_scan.py           → механический предфильтр стилевых кандидатов
russian-style-audit     → тавтология / повторы / коллокации / кальки / монотонность эпитетов
format_scan.py          → шаг 0: механический предфильтр ОФОРМЛЕНИЯ output-файла
                          (регистр предложений и титулов, мысли в кавычках,
                          строки-атрибуции, слипшиеся абзацы, незакрытый курсив,
                          маркеры блоков, согласование рода в обращениях,
                          отбивка маркеров blockgap, реплики в кавычках
                          quotespeech, мысль с нарративом thoughtinline,
                          искажения имён namespell);
                          разбор — russian-prose-rules
drift_scan.py           → ОПЦИОНАЛЬНО: сравнение двух веток или ревизий (дрейф
                          смысловых маркеров: числа/отрицания/имена/термины/лица).
                          Для первичного создания главы НЕ обязателен.
FINAL AUDIT             → проверка результата по всем слоям (итоги GRAMMAR, STYLE, FORMAT;
                          итоговая терминологическая сверка канона — последним шагом после
                          всех исправлений; при сравнении ревизий — также DRIFT)
```

Диаграмма перечисляет слои, а не задаёт жёсткий однопроходный порядок.
При первичной обработке блока (скилл `novel-editor`, режим «Обработка одного
блока») порядок такой: `translation-audit` → `novel-editor` →
`russian-humanizer` → `russian-prose-rules` → ручной разбор
`russian-grammar-control` → `save-progress` (save_block + update_merged) →
`self-review` перед каждой правкой → механические сканеры
(`check_records`, `grammar_scan`, `style_scan`, `format_scan` — им нужен
обновлённый merged) → FINAL AUDIT. В режиме аудита текст уже сохранён,
`self-review` предшествует каждой правке `fix_block.py`, остальные слои идут
сверху вниз с RECHECK после правок. Поиск пропусков — общий детерминированный
`scripts/omission_precheck.py` (см. «Legacy: автоматический semantic audit»);
старый режим генератора промптов «Поиск пропущенных отрывков (GAP-аудит)»
(`tools/agent_workflow.py::prompt_gap_audit`) помечен LEGACY, из
активного меню убран и в текущем pipeline НЕ используется.

**Важно:** `grammar_scan.py`, `style_scan.py`, `format_scan.py` (и опционально
`drift_scan.py`) — механические предфильтры кандидатов, а не источник
окончательного решения;
`check_alignment.py` — структурный диагностический инструмент (alignment
signal ≠ доказательство ошибки). Финальное решение принимает
соответствующий аудит-скилл с учётом контекста; не исправляй текст
автоматически только потому, что сканер что-то отметил. После применённой
текстовой правки соответствующий workflow обязан включать повторную
проверку (RECHECK).

**Опциональное сравнение ревизий (drift_scan.py).** Если агенту требуется
сравнить две ветки или сопоставить текущую главу с исторической базовой
ревизией (например, с коммитом `manual fix`), используется `drift_scan.py`:
`python scripts/drift_scan.py --file vXX-chYY.md --against <SHA/branch>`.
Для первичного создания/редактуры главы скрипт НЕ является обязательным
шагом, так как новый файл создаётся напрямую в `output/`.

**Зона человека и зона агента в маркерах.** `<!-- img_N -->` (места
иллюстраций) ставит только человек — агент их не создаёт и не удаляет.
`---`-разделитель сцены агент МОЖЕТ ставить, когда по JA/EN меняется
локация/место/время, но пропуск разделителя не считается ошибкой;
проверок на их наличие/отсутствие нет. Предфильтр оформления работает по
output-файлу (`output/vXX-chYY.md`), не по merged.

**Сноски переводчика — зона человека: не удалять.** Сноска вида
`^[Пр. пер: …]` (внутристрочный маркер `^[…]`) — намеренная ручная
правка человека, внесённая сознательно; агент не удаляет, не переносит и
не переписывает сноски ни по итогам какой-либо фазы аудита, ни «заодно».
Отсутствие сноски в JA/EN не делает её ошибкой: JA — источник смысла
перевода, но человеко-внесённая добавка — не порождение перевода и не
подлежит сигналу «ADDITION → удалить». Находка любой фазы (Phase 1,
A/B/C, pre-check, сканеры) на сноску закрывается `FALSE_POSITIVE` /
`PRESERVED` с оговоркой «намеренная правка человека»; если сноска по
ошибке была удалена — она восстанавливается дословно. (Инцидент: сноска
«Пр. пер» в v3-ch10, блок 4, удалена в Фазе 2 ошибочно и восстановлена
по указанию пользователя.)

## Legacy: автоматический semantic audit (НЕ реализован)

**К той же категории легаси относится и `prompt_gap_audit()`**
(`tools/agent_workflow.py`) — старый LLM-режим GAP-аудита: самостоятельный
поиск/классификация/исправление пропусков через `fix_block.py`,
`update_merged.py`, отчёт в `output/_audit/vXX-chYY.md` и `_log`. Помечен
`LEGACY / DEPRECATED / NOT USED IN CURRENT PIPELINE`, из активного меню
`agent_workflow.py` удалён, функция сохранена только как исторический
задел (в нём есть полезные эвристики, потенциально пригодные для
`scripts/omission_precheck.py`: сверка сдвига границ блоков, повторная проверка
несколькими ключами, выборка середины, поиск фрагмента в другом блоке,
сцено-чек-лист). Он НЕ переписан под новую архитектуру, НЕ интегрирован в
Analyzer и НЕ создаёт отдельного аудитора. Реальный GAP-аудит не запускается.

Рабочая архитектура смыслового аудита — только:

```text
            JA / RU (+ контекст)
                   ↓
       Common Omission Pre-check          ← scripts/omission_precheck.py
                   ↓                      (детерминированный, НЕ LLM-аудитор)
      ┌────────────┼────────────┐
      ↓            ↓            ↓
Semantic Audit A  Semantic Audit B  Pragmatic Audit C
      └────────────┼────────────┘
                   ↓
              Semantic Analyzer            ← ДВЕ НЕЗАВИСИМЫЕ ФАЗЫ
              ├─ Phase 1 (BLIND): только JA + RU + контекст,
              │  без findings/evidence/sources → analysis/<id>.phase1.json
              └─ Phase 2 (EVIDENCE): A/B/C + omission pre-check
                 сверяются с собственным выводом Phase 1
```

**Common Omission Pre-check** (`scripts/omission_precheck.py`) — общий слой,
запускаемый **до** независимых аудиторских сессий. Он детерминированно сверяет
JA ↔ ED_RU, находит потенциально непокрытые содержательные JA-фрагменты
(обрыв хвоста, пустой RU, числовой якорь), вычисляет приблизительный
`omission_scope` и кладёт evidence в
`output/_audit/sma/<chapter>/precheck/omission-precheck.json` (и `.md`).

- Это **не Auditor D**: не LLM-аудитор, не голос, не вердикт — только
  evidence уровня `severity=CANDIDATE` с `confidence`.
- A/B/C **не обязаны** искать пропуски систематически (их специализации не
  менялись); если пропуск попадается им в рамках обычной работы — находка
  допустима. Отсутствие omission-findings у A/B/C — норма.
- Окончательное решение (CONFIRMED_ERROR / DISPUTED / FALSE_POSITIVE /
  OPTIONAL) принимает Analyzer по сверке JA → RU.

Слои разделены по классу проблем:

- **A** — микро-семантика: лексическая точность, оттенки, эмоции, мимика,
  жесты, интонация, степень выраженности;
- **B** — макро-семантика и логика: субъект/объект, действия, причинность,
  время, местоименные связи, идиомы, метафоры, контекст, намерение/цель
  персонажа как часть содержания ситуации;
- **C (`pragmatic-audit`)** — прагматика: коммуникативный смысл реплики
  (речевой акт), намёк и недосказанность, степень уверенности, просьба vs
  требование, смягчённый vs категоричный отказ, уклонение, разрешение vs
  приказ, обещание, предупреждение, ирония/сарказм, скрытое отношение,
  смягчение/усиление, категоричность, потеря implied meaning; особое
  внимание — японским прагматическим частицам и формам (ね, よ, かな, かも,
  さ, な, でしょう, んです, なんて, まさか, 別に, ちょっと…) в конкретном
  контексте. **C не является третьим универсальным semantic auditor** и не
  дублирует ни A, ни B: грамматика, стиль, орфография и «красивее» — тоже не
  его зона.

**Граница B/C:** B закрывает намерение/цель как часть содержания ситуации,
связи событий и логику происходящего; C — коммуникативную функцию самой
реплики (речевой акт, прагматическая сила, подтекст, implied meaning).

A, B и C независимы: каждый работает в изолированной сессии, получает только
JA / текущий RU / EN / соседние блоки, самостоятельно формирует evidence и
не видит результатов других аудиторов (и не читает Analyzer). Собственный
skill аудитора (`.agents/skills/<свой-навык>/SKILL.md`) разрешён и
обязателен к прочтению — это его собственные инструкции, а не чужие
результаты; всё остальное (чужие skills, `AGENTS.md`, `dictionary.md`,
`addresses.md`, чужие evidence/каталоги `sma/`, Analyzer, pre-check, старые
отчёты) в его вход не входит.

**SMA storage (каноническая раскладка `output/_audit/sma/<chapter>/`):**

```text
a/        evidence Auditor A            (запуски, <run_id>.json)
b/        evidence Auditor B            (запуски, <run_id>.json)
c/        evidence Auditor C            (запуски, <run_id>.json)
precheck/ детерминированное omission-evidence
          (НЕ аудитор, НЕ run kind, НЕ входит в SMA_KINDS)
analysis/ финальные результаты Analyzer (<id>.json / <id>.md)
          + слепые выводы Фазы 1 (<id>.phase1.json — не обычные
          final-запуски; учитывает их helper sma_existing_phase1_runs;
          Фаза 2 адресует Фазу 1 конкретным файлом, при нескольких
          прогонах — самый свежий, см. sma_phase1_files)
```

Результаты — `output/_audit/sma/<chapter>/{a,b,c,analysis,precheck}/`; запуск
промптов — через `tools/agent_workflow.py` (режимы «Смысловой аудит A»,
«Смысловой аудит B», «Прагматический аудит C», «Смысловой анализатор — Фаза 1
(blind)» и «Смысловой анализатор — Фаза 2 (evidence review)»). Каждый запуск
A/B/C получает уникальный `audit_run_id` и не перезаписывает предыдущие.

Analyzer работает в двух режимах и ДВУХ НЕЗАВИСИМЫХ ФАЗАХ
(majority vote запрещён, статусы и действия не менялись):

- **Phase 1 — BLIND**: вход — JA, RU, EN и зеркало блоков (контекст), и больше
  ничего. `JA — authoritative source of truth` (источник истины),
  `RU — text under review` (проверяемый перевод), `EN — reference only`
  (только справочный материал), зеркало блоков — контекст соседних сцен.
  EN в Phase 1 разрешён **только как справка**: он не является evidence A/B/C
  и не является источником истины; при конфликте `JA > EN`
  (основная проверка — JA → RU). Findings A/B/C, evidence pre-check,
  `sources`, списки запусков и прежние analysis-результаты в это задание
  физически не передаются (проверяется self-test по итоговому тексту промпта
  и сверкой с этой документацией). Никаких вердиктов Phase 1 не выносит —
  только `analysis/<id>.phase1.json`.
- **Phase 2 — EVIDENCE REVIEW**: только после Phase 1 приходят A/B/C и omission
  pre-check и сверяются с собственным первоначальным выводом. Задание
  адресует слепой вывод **конкретным файлом**
  (`analysis/<phase1_id>.phase1.json`), а не маской: если слепых прогонов
  несколько, берётся самый свежий (он же «по умолчанию»; порядок —
  `sma_phase1_files`), прогоны не смешиваются, а имя фактически
  использованного файла обязательно фиксируется в `inputs.phase1` результата
  (provenance слепой фазы, как `sources.a/b/c` для аудиторов). Если
  `analysis/<id>.phase1.json` отсутствует — Phase 2 **останавливается**:
  сначала отдельный запуск Phase 1, после его завершения — отдельный
  Phase 2; выполнять Phase 1 внутри evidence-review задания запрещено
  (Phase 2 уже видит evidence, слепость в ней невозможна).
- `A + B` — если запусков C ещё нет: C необязателен для старых глав;
- `A + B + C` — если запуски C существуют; «A+B+C согласны → ошибка» и
  «только C нашёл → false positive» одинаково недопустимы;
- отсутствие pre-check не мешает работе.

Provenance каждого candidate — `sources.a` / `sources.b` / `sources.c`
(все существующие запуски каждой линии; механизма ручного выбора отдельных
`run_id` нет) и `sources.precheck` (маркер
детерминированного pre-check; это evidence, а не голос).

**Сквозный класс пропусков перевода (`MISSING_TRANSLATION`).** Пропуск
содержательного фрагмента JA в RU — отдельный тип finding, а не частный
semantic mismatch. Поле `issue_type` (опционально, обратная совместимость) и
масштаб `omission_scope` (`PHRASE` → `SENTENCE` → `DIALOGUE_FRAGMENT` →
`MULTI_SENTENCE` → `BLOCK_PART` → `FULL_BLOCK` → `MULTI_BLOCK`) канонизированы
в `scripts/semantic_findings.py` (валидатор + `--selftest` + фикстуры).

- Первичное обнаружение — **Common Omission Pre-check**
  (`scripts/omission_precheck.py`), общий детерминированный слой, запускаемый
  **до** A/B/C. A/B/C пропуски систематически **не ищут** (их специализации не
  менялись); пропуск, попавшийся им в рамках обычной работы, — допустимая
  находка. Analyzer дополнительно обязан проверять полноту покрытия в фазе 1
  самостоятельно и вправе создать candidate, даже если pre-check и все
  аудиторы промолчали (majority vote запрещён).
- Pre-check — **evidence, а не голос и не Auditor D**: он выдаёт только
  `severity=CANDIDATE` с `confidence` и никогда не `CONFIRMED_ERROR`.
- Обязательные поля omission-finding: `issue_type` (=
  `MISSING_TRANSLATION`), `omission_scope`, `omission_kind`, `ja_span`,
  `ru_before`, `missing_content` и `not_compression_reason` (`ru_after` —
  если после пропуска есть текст); полный канонический набор проверяет
  `scripts/semantic_findings.py`. `missing_content` (что именно исчезло)
  и `not_compression_reason` (почему это потеря содержания, а не компрессия)
  — ключевые: «JA длиннее RU» сам по себе пропуском не считается; слияние
  абзацев и повтор — тоже.
- Решение по omission (принимает только Analyzer): однозначный пропуск →
  `CONFIRMED_ERROR` (+ `FIXED`, когда правка разрешена); неясно, допустимо ли
  сокращение → `DISPUTED` + `REPORT_ONLY`; компрессия оказалась допустимой →
  `FALSE_POSITIVE` + `PRESERVED`.
- Regression-эталон: pre-check обязан обнаружить v3-ch04 / блок 15 в
  ДОфиксовом состоянии и молчать на текущем исправленном блоке
  (`python scripts/omission_precheck.py --selftest`, кейсы 4 и 7); fixture —
  `scripts/fixtures/semantic_findings/v3-ch04-block15.omission.json`.
  Существующие A/B/C evidence и старые analysis-JSON не изменяются.

Автоматический (orchestrator) контур смыслового аудита вынесен в
[legacy/semantic-audit-auto/](legacy/semantic-audit-auto/LEGACY.md) и имеет
статус **НЕ РЕАЛИЗОВАН / НЕ ПОДДЕРЖИВАЕТСЯ**: `run_semantic_audit.py`,
`merge_findings.py`, `verify_findings.py` (+ скилл `verifier`). Этот контур
использует устаревшую flat-раскладку (`output/_audit/<chapter>-sma-*`) и
другой resolver; он **не используется** в текущем pipeline и **не должен**
на него опираться. Не переносить legacy-код на `sma/<chapter>/...` и не
подключать его к рабочим задачам — это отдельная будущая задача, если будет
решено его реализовать.

## Отчёты: обнаружение ≠ решение

Отчёты аудита явно различают четыре вещи — по каждому кандидату:

```text
style_scan:
ROOT_REPETITION                 ← Detection: что нашёл сканер

classification:
CANDIDATE                       ← Classification: что это такое

investigation:
повтор выполняет риторическую функцию и соответствует JA
                                ← Investigation: что было проверено

disposition:
PRESERVED — FUNCTIONAL          ← Decision: что с этим сделали
```

Формат «ROOT_REPETITION → исправлено» без classification, investigation
и обоснования запрещён.

Для смыслового аудита (SMA) эта граница разведена по фазам: evidence stage
(A/B/C, `omission_precheck`) фиксирует только detection/evidence
(`severity` / `confidence` / `issue_type`) **без обязательного**
classification/disposition — решение ещё не принято; полный набор
classification (status) + disposition (action) по каждому candidate даёт
Analyzer в analysis-отчёте. См. раздел «Classification и disposition».

FINAL AUDIT проверяет **весь файл**, а не только места, найденные
предфильтрами. Если prefilter обнаружил N кандидатов, FINAL AUDIT обязан
позволить установить судьбу каждого (1…N) в терминах disposition;
объединение кандидатов — только с явным перечислением («кандидаты 3, 4, 5
→ один функциональный повтор»). Формулировка «все кандидаты разобраны»
без прослеживаемого решения по каждому кандидату запрещена.

## Известные ограничения нормализации

- Блоки JA/EN/RU выровнены при нормализации (якоря: словарь `dictionary.md`
  - числа, включая японские числительные). Границы блоков между языками
    размыты: абзацы внутри блока могут не совпадать по числу — это норма,
    сравнивай смысл блока, а не абзацы. Редкий блок без EN/RU («—») — граница
    размыта сильнее обычного; проверь его глазами.
- Текст `translates/ru` — машинный перевод и местами переупорядочен, поэтому
  у единичных блоков может не быть своей RU-опоры; смысл всегда проверяется
  по JA (EN помогает).
